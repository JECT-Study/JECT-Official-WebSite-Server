# 선정 결과를 지원 상태와 별도 축으로 관리한다

단체 메일 발송에서 운영팀이 합격 / 예비 합격 / 불합격으로 대상자를 필터링해야 하는데, 기존에는 이 결과를 저장하는 곳이 없었다. 합격 처리는 지원자의 role을 승격시키는 부수효과로만 남았고, 예비 합격은 개념 자체가 없었으며, 불합격에 해당하는 `ApplyStatus.REJECTED`는 실제로는 지원서를 무효화하는 반려 동작이었다. 지원서가 작성·제출 과정에서 놓인 단계(지원 상태)와 운영팀이 그 지원을 평가한 결과(선정 결과)는 서로 독립적으로 변하는 사건이므로, `ApplyStatus`에 값을 더하는 대신 `Apply`에 선정 결과를 별도 축으로 추가한다.

## Considered Options

- **`ApplyStatus`에 합격 / 예비 합격 값을 추가** — 컬럼을 늘리지 않아도 되지만, 지원서 제출 여부와 평가 결과가 한 필드에서 서로를 덮어쓴다. 제출된 지원만 평가 대상이라는 관계도 표현할 수 없다.
- **별도 평가 엔티티로 분리** — 차수별 평가 이력까지 담을 수 있으나, 현재 요구되는 것은 지원당 하나의 현재 결과뿐이라 구조가 과하다.

## Consequences

- `Apply`에 상태 성격의 필드가 둘 존재하게 된다. 두 필드는 서로를 변경하지 않는다. 특히 **선정 결과를 불합격으로 두는 것은 지원 상태를 변경하지 않으며**, 지원서를 무효화하지도 않는다.
- 기존 데이터는 모두 미정으로 채운다. 과거 합격자의 흔적은 role 승격뿐인데, 승격 경로가 별도 합류·기존 기수 등 여러 갈래라 합격으로 추정하면 실제로 합격한 적 없는 지원자가 합격으로 기록된다. 그 상태에서 합격 안내 메일이 발송되는 사고를 막기 위해 과거 이력은 복원하지 않는다.
- 합격으로 세팅하는 경로는 기존의 구성원 승격(role, memberType 변경)을 그대로 수행한다. 운영팀에게 "합격 처리"는 곧 구성원 승인이며, 이 절차를 바꾸지 않는다.

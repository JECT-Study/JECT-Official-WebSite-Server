# 발송 여부가 불확실한 메일은 자동 재발송하지 않고 격리한다

SES 수락 직후 DB 결과 기록 전에 프로세스가 중단되면 발송 여부를 확정할 수 없고, 현재 SendEmail API에는 호출자가 지정하는 멱등성 토큰이 없다. 2026-10-02 운영자 결정에 따라 불확실 결과는 `UNKNOWN`으로 격리하고 자동 재발송하지 않는다. 처리 완료보다 중복 안내 메일 방지를 우선하며, 실제 발송이 없었던 작업도 확인 전까지 지연될 수 있음을 수용한다.

## 적용 경계

- 발송 의도와 수신자별 제목·본문 snapshot은 Outbox에 원자적으로 저장한다. 아직 발송 시도를 획득하지 않은 `PENDING`만 자동 실행 후보가 된다.
- 외부 호출 전에 claim을 DB에 커밋한다. 발송 가능성이 있는 실행의 lease 만료는 재발송 신호가 아니라 불확실 결과 격리 사유다. 호출 전 중단과 호출 후 중단을 구분할 증거가 없으면 보수적으로 격리한다.
- SES 응답 유실, 호출 결과 불명, SES 수락 후 DB 결과 기록 실패는 자동 재발송하지 않는다. SDK 내부 자동 재시도도 이 원칙을 우회하지 않도록 검토한다.
- 오래된 claim의 결과 갱신은 claim 식별자와 현재 상태를 함께 확인해 거부한다. 격리된 작업을 늦게 도착한 실행 결과로 무조건 덮어쓰지 않는다.
- 확실하게 거부되었거나 외부 호출이 시작되지 않았다는 근거가 있는 실패만 별도 오류 분류·횟수·대기 시간 정책에 따라 재시도할 수 있다. 모든 네트워크 오류나 모든 5xx를 안전한 재시도로 간주하지 않는다.
- 격리는 성공이나 확정 실패와 구분해 관리자 조회·집계에서 드러내고, 자동 실행 후보에서 제외한다. 운영자 확인·해제는 명시적인 별도 조치다. 이 ADR은 확인 없이 재발송할 권한을 부여하지 않는다.

## 보장하지 않는 것

DB Outbox와 claim만으로 SES 수락 또는 최종 배달의 정확히 한 번 처리를 보장하지 않는다. `SENT`는 SES 호출 성공 기록이며 수신함 도착 증명이 아니다. SDK 재시도, 기존 동기 발송 경로, 다중 서버 실행도 같은 정책을 충족해야 하며, 이 문서 추가만으로 런타임 적용이 완료되지는 않는다.

## 구현 순서

1. claim·lease와 불확실 상태 저장, 오래된 claim 차단을 실제 MySQL에서 검증한다.
2. 기존 동기 요청과 worker가 같은 영속 실행 경계를 사용하도록 연결하고, 미처리 대상 복구와 불확실 결과 격리를 검증한다.
3. 확정 실패의 재시도 분류·횟수·대기 시간과 관리자 조회·관측을 보강한다. 격리 대상의 운영자 확인 절차를 별도로 제공한다.

예약 시각 기반 발송과 신규 공급자 도입은 #670 범위에 추가하지 않는다. 기존 feature branch 전체를 병합하지 않고 검증된 기반에 필요한 변경만 재적용한다.

## 근거

- 사용자 승인: 2026-10-02 “권장안대로 진행해주세요”. 권장안은 불확실 결과의 자동 재발송 금지와 운영자 확인이었다.
- [SES SendEmail 요청·응답 계약](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html): 요청 멱등성 토큰이 없고 `MessageId`는 수락 시 생성된다. 수락과 실제 전송도 구분된다.
- [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html): Outbox는 DB 저장과 이벤트 발행 경계를 보완한다. 외부 SES의 중복 제거 보장으로 해석하지 않는다.

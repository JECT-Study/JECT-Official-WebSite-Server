# 발송 여부를 알 수 없는 메일의 운영자 확인 절차

`UNKNOWN / MAIL-21`은 실패 확정이 아니라 확인 필요 상태다. 서버가 메일 발송 서비스의 응답을 받지 못했거나, 수락 후 결과 저장 전에 중단된 경우 실제로 보냈는지 알 수 없다. 확인 전에는 자동·수동 재발송을 하지 않는다. 이 문서는 기존 조회 기능으로 확인하는 절차이며 상태 해제·재발송 API나 새 발송 승인 정책을 정의하지 않는다.

## 상황 예시

합격 안내를 100명에게 보내던 중 서버가 종료됐다. 70명은 성공, 20명은 아직 처리 중, 10명은 발송 여부를 확인할 수 없다. 확인 필요 10명은 자동 재발송 대상이 아니다. 받은 사람이 이미 있을 수 있으므로 실패한 10명으로 간주해 다시 보내면 안 된다.

다른 대상이 처리 중이면 작업 전체는 `PROCESSING`이고 `unknownCount=10`일 수 있다. 모든 대상의 결과가 정해진 뒤 확인 필요 대상이 남으면 작업은 `UNKNOWN`이다. 작업 목록에서 `status=UNKNOWN`만 조회하면 처리 중인 작업의 확인 필요 대상을 놓칠 수 있다.

## 1. 작업과 확인 필요 대상을 찾는다

발송을 요청한 관리자 계정의 기존 인증으로 조회한다. 다른 관리자 작업은 조회할 수 없으며 없는 작업과 같은 `404 / MAIL-9`를 반환한다. 권한 우회나 DB 직접 수정으로 해결하지 않는다.

작업 ID를 아는 경우:

```http
GET /admin/mails/dispatches/123
GET /admin/mails/dispatches/123/targets?status=UNKNOWN&page=0&size=10
```

ID를 모르는 경우 본인 작업 목록에서 `UNKNOWN` 작업과 처리 중인 작업을 각각 확인한다. 요청한 모집 공고를 알면 기존 `recruitId` 조건을 함께 사용한다.

```http
GET /admin/mails/dispatches?status=UNKNOWN&page=0&size=10
GET /admin/mails/dispatches?status=PROCESSING&page=0&size=10
```

공통 응답의 `data.content`, `data.hasNext`를 확인하고 `hasNext=true`이면 `page`를 증가시켜 같은 조건으로 계속 조회한다. 작업 목록은 최신순이며 수신자 결과는 대상 ID 오름차순이다. 처리 중 작업은 `unknownCount>0`인지 확인한 뒤 대상의 `status=UNKNOWN` 결과를 조회한다. 목록과 상세는 조회 시점에 따라 달라질 수 있으므로 판단 직전에 상세를 다시 확인한다.

## 2. 상태와 기록을 구분해서 읽는다

확인할 항목은 작업 ID·대상 ID·지원 ID, 요청한 관리자, 모집 공고, 요청·시작·종료 시각, 대상 상태와 오류 코드다. `failureReason=MAIL-21`은 확인 필요 사유이며 확정 실패 코드가 아니다.

- `attemptCount`: 발송 시도를 획득한 횟수다. 실제 배달 횟수가 아니다. V49 이전 claim 기록의 1은 migration 보정값이다.
- `nextAttemptAt`: 안전한 거부에 대한 재시도 대기 시각이다. null이면 성공이나 재발송 허가라는 뜻이 아니다.
- `lastAttemptFailureReason`: 마지막 저장된 시도 오류다. 오류 코드만으로 재시도 가능 여부를 판단하지 않고 현재 대상 상태를 함께 확인한다. `UNKNOWN`은 자동 재시도 대상이 아니다.
- `sentAt`: 성공 기록 시각이다. null이라고 외부 발송이 없었다고 단정하지 않는다.
- Outbox 없는 과거 이력의 재시도 정보 null: 정보 부재다. 미시도 횟수 0과 다르다.

작업·대상 ID로 `[MAIL_DISPATCH_STATE]` 로그를 찾아 조회 결과와 대조한다. 주소·제목·본문·token을 로그에 추가하지 않는다. counter와 로그는 유실될 수 있으며 DB 조회 결과가 원본이다. `SENT`도 수신함 도착이나 열람 증명은 아니다.

## 3. 외부 발송 근거를 확인한다

운영 환경에 이미 보존된 외부 발송 기록이 있고 조회 권한이 있는 경우에만 관련 근거를 대조한다. 현재 `SesEmailSendService.sendEmail`은 SES 응답의 `MessageId`를 반환·저장하지 않는다. 애플리케이션 조회만으로 특정 SES 메시지를 자동 대조할 수 있다는 가정은 금지한다.

SES 수락 기록이 확인되더라도 실제 배달과는 구분한다. 수신자가 못 받았다고 말하거나, 성공 로그·메트릭·외부 기록이 검색되지 않는다는 이유만으로 미발송을 확정하지 않는다. 수집 장애·보존 기간·연결 정보 부재도 가능하다. 발송 여부를 확정할 근거가 없으면 `UNKNOWN`을 유지한다.

## 4. 확인 내용과 미결정을 남긴다

승인된 내부 기록 도구에 작업·대상 ID, 확인 담당자·시각, 근거의 위치, 확인 결과와 아직 모르는 내용을 기록한다. 공개 이슈·PR·일반 로그에는 주소·메일 본문·인증값을 복사하지 않는다. 확인 결과 기록은 원래 발송 상태를 변경하는 동작이 아니다.

확인 메모 예시:

```text
작업 / 대상: 123 / 456
확인 담당자 / 시각: 담당자 식별자 / 확인 시각
상황: 외부 수락 후 결과 저장 실패 가능성
확인 근거: 접근이 제한된 내부 기록의 위치
판정: 발송 여부 확인 불가
조치: UNKNOWN 유지, 재발송하지 않음
남은 확인: 외부 메시지와 해당 대상의 연결 근거
```

현재 API에는 `UNKNOWN` 해제·성공 확정·확인 사유 저장·재발송 전용 기능이 없다. 기존 DB 상태나 시도 횟수를 직접 고치지 않는다. 새 Idempotency-Key로 발송 요청을 만드는 것은 조회나 안전한 재시도가 아니라 별도의 실제 발송이다. 원래 key를 재사용해도 확인 필요 작업을 다시 실행하지 않는다. 기존 fingerprint가 없으면 `409 / MAIL-20`으로 비교 불가 요청을 거부하는 계약도 유지한다.

원본 이력을 보존한 새 발송 방식, 승인 주체, 확인 사유의 저장 위치, 원래 작업과 새 작업의 연결은 후속 정책 결정 대상이다. 이 안내만으로 새 발송 권한을 부여하지 않는다.

## 검증 경계

조회 경로·소유권·페이지·상태 및 재시도 필드는 현재 컨트롤러·서비스·QueryDSL과 관련 테스트 계약을 따른다. 격리 정책은 ADR 0002를 따른다. 이 문서 검증은 운영 SES 메시지 대조나 실제 알림 도착·재발송 검증을 뜻하지 않는다.
